# Fight 101 — Unity port

This folder is the Unity 2D rewrite of Fight 101. The original JS game at
the repo root is still the source of truth for behavior — we read it when
porting each system.

Full plan: `~/.claude/plans/can-you-swap-game-serialized-lightning.md`

## Status: U1 — shipped ✓

WebGL build runs: blue 36×36 player on a green background, WASD/arrows to
move, clamped to a 4800×4800 world. No Unity Editor required to rebuild —
everything is driven by CLI and the `U1Setup` editor utility.

## Build & run locally

```sh
cd unity
./build-webgl.sh
cd Build/WebGL && python3 -m http.server 8001
```

Open http://localhost:8001/ — Unity loads, blue square appears, WASD moves
it. Build takes ~3–8 min the first time, faster on subsequent runs (Unity
caches the asset import in `Library/`).

Note: the build is uncompressed (~62 MB) so plain `http.server` can serve
it without `Content-Encoding: br` headers. For real deployment (GitHub
Pages, itch.io) flip `WebGLCompressionFormat` back to `Brotli` in
[Builder.cs](Assets/Editor/Builder.cs) — those hosts set the right headers.

## What's in here

```

  Assets/
    Editor/

      U1Setup.cs           — one-shot utility that builds Player.prefab and

                             configured Camera) via Unity's APIs. Safer
                             than hand-authoring scene/prefab YAML.
    Scripts/

        PlayerInput.cs     — wraps Input.GetKey / GetKeyDown (legacy)
    Sprites/Player.png     — 36×36 blue square (procedural, generated by
                             python in setup)
    Scenes/Boot.unity      — Player + GameManager + Camera
    Prefabs/Player.prefab  — built by U1Setup.cs
  Packages/                 (Unity package manifest, auto-managed)
  ProjectSettings/          (Unity settings, edited: activeInputHandler=2,
                             canvas 1280×720)
  Library/                  (Unity asset cache, gitignored)
  Build/                    (build-webgl.sh output, gitignored)
  build-webgl.sh            — CLI WebGL build wrapper
  .gitignore                — keeps Library/, Build/ etc. out of git
```

## Re-running U1Setup

If `Boot.unity` or `Player.prefab` ever get out of sync with the scripts
(e.g. a component was renamed or removed), regenerate them by running
the one-shot utility:

```sh
/Applications/Unity/Hub/Editor/<version>/Unity.app/Contents/MacOS/Unity \
  -batchmode -quit -nographics \
  -projectPath . \
  -executeMethod U1Setup.Run \
  -logFile /tmp/u1setup.log
```

Safe to re-run — it overwrites the prefab and rebuilds the scene from
scratch.

## How U1 was set up (history, for future sessions' reference)

For reference when planning later sessions, here's what was manual vs
automated for U1:

**Manual (dad):**
- Install Unity Hub (`/Applications/Unity Hub.app`)
- Install Unity 6 LTS + WebGL Build Support via Hub
- Install Rosetta 2 (`sudo softwareupdate --install-rosetta --agree-to-license`)
  — required even though Unity is native arm64; some sub-processes are Intel-only

**Automated (Claude via CLI):**
- Project creation (`Unity -createProject -cloneFromTemplate ...`) bypassing
  Hub's cloud-handshake (which hung at 0% CPU for 2 min)
- Scaffold merge (Scripts, Editor, build-webgl.sh, .gitignore, README)
- ProjectSettings patches (Input Handling = Both, canvas 1280×720)
- Player.png generation (python one-liner writing PNG bytes)
- Player.png.meta patches (TextureType=Sprite, PPU=1, filterMode=Point)
- Boot.unity scene authoring (via U1Setup.cs Editor script)
- Player.prefab authoring (via U1Setup.cs)
- WebGL build (`./build-webgl.sh` invoking `Unity -batchmode -executeMethod Builder.BuildWebGL`)

The takeaway: Unity 6 from Unity 6.4 onward can be fully scripted from the
command line as long as you have a license activated (Hub does this once).
Future sessions should follow the same pattern: write a `UNSetup.cs` Editor
utility per session, invoke via `-executeMethod`.

## Notes on the licensing handshake

Batch-mode Unity logs `[Licensing::Module] Error: Failed to handshake to
channel` because it tries to reach a Hub IPC channel that isn't running.
Builds still succeed in our case — the license is cached locally. If a
future build fails with a real licensing error, the fix is to open Unity
Hub once and let it refresh the license.
